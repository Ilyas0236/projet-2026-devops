# 🔍 Audit complet du projet Wydad Digital — 2026-08-24

> Audit réalisé avant de continuer la roadmap : backend (9 services), frontend/design, tests ISTQB, préparation déploiement.
> Verdict global : **le projet est bien plus avancé que prévu** — une vraie base solide — mais avec **3 failles de sécurité bloquantes**, une **migration thème clair inachevée** et des **tests à rééquilibrer selon ISTQB**.

## 2. 🚨 FAILLES DE SÉCURITÉ BLOQUANTES (à corriger AVANT toute nouvelle feature)

| # | Gravité | Problème | Fichier |
|---|---|---|---|
| S1 | 🔴 Critique | **Login n'a pas vérifié `user.isActive()`** → un compte désactivé par l'admin peut encore se connecter | auth-service `AuthService.login` |
| S2 | 🔴 Critique | **Bug refresh token** : `refreshToken()` valide avec type `access` → un access token volé permet de régénérer tokens indéfiniment ; le vrai refresh token serait rejeté | auth-service `AuthService.refreshToken` |
| S3 | 🔴 Critique | **Niveau d'adhésion choisi librement à l'inscription** y compris LEGENDE (prix 0) → contournement total du paiement d'adhésion | auth-service `RegisterRequest.membershipLevel` |
| S4 | 🟠 Majeur | Révocation de sessions n'invalide pas les refresh tokens existants | auth-service sessions |
| S5 | 🟠 Majeur | `member-card`/`attestation`/`points/add` contrôlent le rôle via headers optionnels lus manuellement au lieu de `@PreAuthorize` → défense-en-profondeur insuffisante si un port est exposé | auth + gamification |
| S6 | 🟠 Majeur | OTP orphelin : aucun flux d'activation de compte ni reset password (l'email d'un compte ne peut pas être récupéré) | auth-service |
| S7 | 🟡 Mineur | `GET /otp/mock-code` permitAll côté service ; incohérence classements (liste ADMIN, détail public) | auth + content |

## 3. 🐛 Autres anomalies

- **Modèles fantômes shop-service** : `WishlistItem` et `ProductReview` (entités + repos) sans aucun endpoint — à câbler ou supprimer
- **KYC purement déclaratif** : `filePath` envoyé par le client comme chaîne, aucun fichier réellement stocké → sera remplacé par Cloudinary (Phase 1 roadmap)
- **Paiement carte = mock** ChariBaaS ; billetterie E-cash uniquement (décision produit à assumer pour la mise en ligne)
- Pas d'entité Match côté sports-service (les stats référencent des matchs de content-service) — périmètre OK mais à documenter
- Dockerfiles backend = JAR pré-compilé (`COPY target/*.jar`) → le build Maven doit être lancé avant `docker compose build`. La CI produit déjà les images multi-arch ? Non : à vérifier/buildx ARM pour Oracle Cloud

## 4. 🎨 Design vs grands clubs européens — écarts priorisés

Le socle (tokens, layout, navbar/footer) est **solide**. Les 10 écarts :

1. **🔴 Migration thème clair inachevée** : seul Home est blanc ; ~18 pages publiques encore sombres dont **Actualités** (patchwork blanc/noir). Finir avant toute nouvelle feature.
2. **Photographie professionnelle absente** : 1 seul jpg hero, dossiers players/sponsors vides, placeholders initiales « WAC » — un grand club vit par l'image
3. **Page article à refaire entièrement** (`actualite-detail`) : styles inline hardcodés hors design system, emojis ⏳, pas de partage social ni articles liés — c'est la 2ᵉ page la plus visitée d'un site de club
4. **Accessibilité quasi nulle** : ~2 aria-* dans tout le layout, pas de skip-link, contrastes invalides WCAG AA (`ink-tertiary #88888E` sur blanc ≈ 3.4:1)
5. **Émojis comme icônes** (⚽✍️⏳) au lieu d'une iconographie cohérente (Material Icons déjà chargé)
6. Hero trop générique : pas de vidéo d'ambiance, countdown prochain match, compteurs titres
7. Pas de module match-day en home (score live/résultat/badge compétition colorée)
8. **Monolingue français** — l'ARABE est indispensable pour le Wydad (aucune infra i18n)
9. États de chargement/erreur silencieux (home affiche des sections vides si API down)
10. Nettoyage : `styles.css` fantôme à supprimer, styles inline à extraire, classes navbar dupliquées ×8

## 5. 🧪 Tests vs ISTQB — état par niveau

| Niveau ISTQB | État | Constat |
|---|---|---|
| Unitaire | 🔴 Quasi absent | ~90 % des tests = `@SpringBootTest` (pyramide inversée). Seuls OtpService/JwtUtils/FileTypeValidator ont des tests purs |
| Intégration | 🟠 Partiel | Bonnes pratiques réelles (sécurité, ownership, concurrence wallet) mais sur H2 alors que prod = PostgreSQL ; Testcontainers déclarés dans auth pom mais jamais utilisés |
| Système/E2E | 🔴 Inexistant | Aucun test cross-services (achat→wallet→notification), zéro spec Angular (boilerplate supprimé) |
| Acceptation | 🔴 Inexistant | Pas de Gherkin/Cucumber |
| Couverture | 🔴 Non mesurée | JaCoCo absent partout, aucun seuil |
| CI | 🟠 Correcte back, vide front | `mvn package` lance les tests Java ✔ ; `ng test` jamais branché |

Densité très inégale : payment (domaine sensible !) = 6 méthodes seulement, api-gateway = 1 fichier.

## 6. ✅ Plan d'action recommandé (ordre strict)

**Vague 0 — Sécurité (bloquant)** : corriger S1→S7 ci-dessus, avec tests de non-régression pour chaque correction (ISTQB : chaque bug = cas de test).
**Vague 1 — Cohérence design** : finir la migration thème clair des ~18 pages (Actualités en premier), refaire `actualite-detail` dans le design system, remplacer émojis, contraste WCAG AA, supprimer styles.css fantôme.
**Vague 2 — Dette tests** : JaCoCo + seuil, découper quelques SpringBootTest en unitaires Mockito, activer Testcontainers PostgreSQL, premiers specs Angular + `ng test` en CI.
**Vague 3 — Roadmap communauté** (reprendre `ROADMAP-DEPLOIEMENT.md`) : Phase 0 simplifiée — rôles ENTRAINEUR/PRESIDENT/JOURNALISTE + statut validation compte ; KYC remplacé par upload réel Cloudinary.
**Vague 4 — Déploiement Oracle Cloud** (section 4 du ROADMAP).

> Règle de travail adoptée : chaque vague terminée = tests verts en CI + commit propre + push, pour ne plus accumuler de retard.
