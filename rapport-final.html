Architecture générale

Une application unique côté visiteur, neuf services indépendants derrière une passerelle sécurisée, un socle Docker prêt pour la production.

BriqueTechnologieRôle
Passerelle APISpring Cloud GatewayPoint d'entrée unique (port 8080) : validation JWT, injection d'identité, blocage des routes internes
Services métier ×8Java 21 · Spring Boot 3auth, content, payment, shop, ticket, notification, sports, gamification
FrontendAngular 19 standalone · Tailwind CSSSPA servie par nginx, proxy /api vers la passerelle
DonnéesPostgreSQL 16 (une base par service)Isolation des données par domaine
Cache & sessionsRedis 7Support auth-service
ProductionDocker ComposeHealthchecks, ordre de démarrage fiable, secrets via .env

Chaîne d'identité entre services

  • Le JWT fait foi : signé HS256 avec secret partagé, porteur des claims typ (access/refresh), rôle et identifiant utilisateur.
  • La gateway assainit les headers d'identité envoyés par le client (X-User-*) puis réinjecte l'identité extraite du token validé.
  • Les services font confiance à ces headers via leur filtre UserContextFilter ; l'autorisation fine est faite par rôle côté service.
  • Les appels internes service-à-service sont protégés par un secret partagé X-Internal-Secret comparé en temps constant ; leurs routes sont bloquées depuis l'extérieur par la gateway.
  • Aucun port de service exposé sur l'hôte en production : tout passe par la gateway ou nginx.

Backend — service par service

Chaque service possède ses entités, ses règles métier serveur et ses propres tests. Ci-dessous l'inventaire réel du code, fonctionnalité par fonctionnalité.

🔐 auth-service

port 8081 · base auth_db · 26 tests
  • Inscription / login / refresh avec tokens access + refresh typés séparément
  • Sessions actives persistées : liste consultable, révocation unitaire, « déconnexion partout »
  • Niveaux d'adhésion ROUGE/OR/DIAMANT/LEGENDE/JUNIOR avec montée de niveau contrôlée (/upgrade)
  • Carte de membre avec QR code (ZXing) et attestation d'adhésion PDF générée côté serveur
  • OTP hashé SHA-256, TTL 10 min, max 5 tentatives — réutilisé par le nouveau flux de réinitialisation de mot de passe
  • KYC : dépôt de pièce d'identité, validation ADMIN
  • Gestion admin des comptes : création directe (joueurs, staff…), activation/désactivation, changement de rôle
  • Compte administrateur semé au démarrage — mot de passe obligatoirement fourni par variable d'environnement, jamais codé en dur

📰 content-service

port 8082 · base content_db · 56 tests
  • Actualités par section sportive (football, basket, handball…) — brouillons non exposés publiquement
  • Calendrier & résultats : la saisie d'un résultat déclenche automatiquement la résolution des pronostics
  • Classements par compétition, lecture publique
  • Palmarès, légendes du club, sponsors : CRUD admin + pages publiques dédiées
  • Effectif public géré par l'admin
  • Paramètres du club (paliers d'adhésion, coordonnées, infos stade, saison) : source de vérité consommée par tout le site
  • Réclamations & support : dépôt membre, réponse officielle ADMIN, anti-IDOR, notification email
  • Médiathèque : upload sécurisé par validation des magic bytes réels du fichier (Content-Type forgé rejeté), limite 1 Mo, protection path traversal

💳 payment-service

port 8083 · base payment_db · 6 tests
  • Wallet E-cash par membre : solde, historique de transactions, recharge ADMIN
  • Verrou pessimiste (PESSIMISTIC_WRITE) sur toutes les mutations de solde — concurrence prouvée par test dédié
  • Dons avec reçu fiscal PDF, wallet débité depuis le JWT uniquement (anti-IDOR)
  • Paiement carte mock ChariBaas, plafonné et désactivable
  • Débit/remboursement internes pour ticket-service et shop-service

🎟️ ticket-service

port 8084 · base ticket_db · 10 tests
  • Événements (matchs, types et statuts), recherche publique
  • Achat multi-billets avec verrous pessimistes sur événement et section — compteurs de places toujours cohérents
  • Prix calculés côté serveur, paiement E-cash réel
  • Billet PDF + QR code générés par ZXing/OpenPDF, validation au scan par le staff
  • Annulation avec remboursement E-cash automatique et restitution du stock

🛍️ shop-service

port 8085 · base shop_db · 15 tests
  • Catalogue produits avec variantes, images, catégories — consultation publique anonyme
  • Panier complet (ajout, quantité, suppression)
  • Commande atomique : verrouillage de toutes les variantes triées par identifiant (anti-deadlock), prix recalculé depuis la base, décrément de stock + débit wallet ensemble, rollback si le paiement échoue
  • Codes promo créés/activés par l'ADMIN, remise validée 1–100 %, verrouillés à l'usage
  • Suivi de commandes avec transitions de statut validées serveur (préparation → expédition → livraison / annulation → remboursement)
  • Personnalisation maillot et points de fidélité crédités après chaque achat réel

⚽ sports-service

port 8086 · base sports_db · 40 tests
  • Espace joueur complet : convocations reçues avec réponse (confirmé / absent / retard + justification), présence, documents partagés par le staff, statistiques personnelles, profil restreint
  • Espace staff : envoi de convocations par catégorie, partage de documents, saisie des statistiques de match, gestion de l'effectif
  • Statut médical APT/INAPTE strictement réservé au staff médical de la catégorie
  • Messagerie interne joueur ↔ staff filtrée par catégorie + annonces officielles
  • Sondages publics : vote unique garanti au niveau SQL, consultation anonyme des sondages actifs
  • Académie : inscription multi-étapes par un parent avec pièces justificatives réellement uploadées/téléchargeables, validation du dossier par staff/admin
  • Séances d'entraînement notifiées et gérées

🎮 gamification-service

port 8087 · base gamification_db · 15 tests
  • Points et niveaux de fidélité : barème 1 point / 10 DH dépensés, crédités automatiquement après chaque achat boutique/billet
  • Pronostics soumis au nom de l'utilisateur JWT uniquement, résolus automatiquement contre les résultats réels saisis dans content-service
  • Badges : catalogue administrable, attribution automatique (dont badges de fidélité B.8)
  • Leaderboard public des supporters

🔔 notification-service

port 8088 · base notification_db · 25 tests
  • Notifications in-app / email / push avec orchestrateur multi-canaux respectant les préférences de chaque membre
  • Broadcast ADMIN avec fan-out réel vers tous les utilisateurs actifs (via auth-service)
  • Notifications transactionnelles déclenchées par les autres services : achat de billet, commande boutique…
  • Newsletter publique : inscription anonyme depuis le footer, désinscription par token

Socle technique

  • Client API centralisé (api.service.ts) couvrant les 9 microservices, URLs externalisées dans les environments
  • Authentification : interceptor qui joint le JWT et intercepte les 401 ; état utilisateur réactif (BehaviorSubject)
  • UX soignée : toasts, dialogues de confirmation, bannières d'erreur avec bouton « Réessayer », squelettes de chargement, page 404
  • nginx : fallback SPA, cache assets 30 jours immuable, gzip, proxy /api résiliant au démarrage de la gateway, uploads limités à 10 Mo
  • Dockerfile multi-stage : build Node 20 puis image nginx 1.27 avec healthcheck

Design system

Tokens Tailwind complets : marque rouge #DC143C + or, palette claire paper-*/ink-* (thème blanc/rouge des pages publiques) et palette sombre historique surface-* conservée pour l'admin, polices Inter/Oswald/JetBrains Mono, tailles fluides clamp(), classes de composants (.paper-card, .wydad-btn, système admin complet), animations et motif zellige.

Migration thème clair en cours : layout public, accueil, espace fan, inscription académie, fiche produit et mes-billets sont passés au clair ; environ 35 vues restent encore sur la palette sombre (voir §07).

Sécurité

L'audit du 24 août 2026 a recensé sept failles ; elles sont toutes corrigées et couvertes par des tests de non-régression (commits 7bd51a9 + 25d57c7).

#Faille corrigéeCorrection apportéeTest
S1Un compte désactivé pouvait encore se connecter et rafraîchir ses tokensRefus au login et au refresh, message identique aux mauvaises credentials (pas d'énumération de comptes)Vert
S2Un access token volé permettait de régénérer des tokens à l'infini/refresh exige désormais typ=refreshVert
S3Le niveau d'adhésion était choisi librement à l'inscription (LEGENDE gratuit = contournement du paiement)Niveau forcé ROUGE côté serveur ; champ supprimé du DTO et du formulaire ; montée de niveau uniquement via /upgrade après paiementVert
S4« Déconnexion partout » n'invalide pas les refresh tokens existantsRefresh rattaché aux sessions révocables : sessions révoquées ⟹ refresh refuséVert
S5Carte membre, attestation et points/laddition contrôlaient le rôle via headers optionnels lus à la mainHeaders d'identité gateway rendus obligatoires (appel direct au service = 401) ; contrôle par contexte JWT homogèneVert
S6L'OTP était orphelin : aucune récupération de mot de passe possibleNouveau flux complet : envoi OTP → POST /api/auth/password/reset → mot de passe changé + toutes les sessions coupéesVert
S7Incohérences d'exposition (mock-code OTP, classements)Canal mock isolé derrière flag désactivé en prod ; classements cohérents en lecture publique / écriture ADMINVert

Défenses déjà en place avant l'audit

  • Anti-élévation de privilèges : purge systématique des headers X-User-* client à la gateway
  • Anti-IDOR généralisé : profil, upgrade, dons, wallet, pronostics, réclamations, documents académie — l'utilisateur est toujours dérivé du JWT
  • Verrous pessimistes sur wallet, stock billetterie et variantes boutique (anti-surréservation)
  • Uploads durcis : magic bytes réels, limites de taille, path traversal bloqué
  • Routes internes /internal/** bloquées depuis l'extérieur, secret inter-services comparé en temps constant
  • Secrets hors code : JWT_SECRET et ADMIN_SEED_PASSWORD obligatoires via .env, aucun fallback committé
  • OTP jamais renvoyé dans la réponse HTTP ni stocké en clair ; messages d'erreur homogènes (401/403/404 sémantiques)

CI/CD & déploiement

Un pipeline GitHub Actions complet construit, teste et publie les 10 images Docker à chaque push sur main.

Pipeline (`.github/workflows/ci.yml`)

  • Étape 1 — build & tests : Maven package les 9 services (les tests Java tournent à chaque push, y compris en pull request)
  • Étape 2 — publication Docker Hub : 10 images (9 services + frontend), taguées latest + sha du commit, avec cache GHA
  • Frontend : build Angular production vérifié, image nginx multi-stage publiée

Déploiement production (docker-compose)

  • Ordre de démarrage fiable : healthchecks wget/redis/pg_isready + depends_on: service_healthy
  • Surface d'attaque minimale : seuls la gateway (8080) et le frontend (4200) sont exposés ; les 8 autres services communiquent en réseau interne
  • Secrets exigés via ${VAR:?} — la stack refuse de démarrer sans .env complet
  • Volumes persistants PostgreSQL + scripts d'initialisation des bases
  • pgAdmin disponible pour l'administration des données
Cible retenue : Oracle Cloud Always Free (ARM A1, jusqu'à 4 OCPU / 24 Go RAM) — largement suffisant pour cette stack. Les détails opérationnels sont dans ROADMAP-DEPLOIEMENT.md (buildx ARM, Caddy HTTPS, checklist post-déploiement). Rappel de la règle établie : les clés SSH ne quittent jamais ta machine, même vis-à-vis de moi.
